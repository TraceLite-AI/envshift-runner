# Windows 视口修正与评分口径

发现时间：2026-09-14（初轮模型运行期间，修正后模型尚未运行）。

初轮 G15/Windows 的 `step60.png` 显示 Next 按钮被桌面任务栏遮住，最终点击使 Chrome 最小化，露出 runner 窗口。初始装置请求 1200×850 浏览器窗口，而 Windows 桌面是 1024×768；G14 的底部行也被遮挡。三个 Windows 任务共用此初始化。

因此统一处理全部三个 Windows 初轮结果：保留原始 reward、valid_model_run 和所有截图/日志，但作为受视口装置影响的诊断记录，不纳入修正后的九格主结果或累计有效 badcase 轨迹数。不能只因为某格失败就选择性剔除；这条规则在新的 Windows 模型结果产生之前写定，适用于三题的原始 Windows 运行。

修正只是在模型开始前用原生 Win+Up 最大化 Chrome，记录实际窗口边界并检查 windowState 为 maximized。没有改变题面、fixture、业务逻辑、判分、模型、动作空间、60 步预算或记忆。新增代码在 Windows 条件下执行；其他两系统未增加行为。

修正代码单独保存在 `diagnostics/window-fit/`，独立分支与运行记录。先对三道 Windows 题重新执行 GUI 正反对照，再各跑一次模型。主结果由原轮 Ubuntu/macOS 六格与修正后的 Windows 三格组成；初轮九格始终保留，可与修正后分开查看。

新运行不是同配置稳定性复测，不能拿修正前后一次结果变化证明视口是唯一原因。G14/G15/G16 的新题身份仍由有效且未被装置问题排除的失败支撑；具体数量以最终主结果计算。此前运行中计数是临时值，若有变化需在报告明确交代排除了哪些装置诊断轨迹。

两个版本的四个业务/代理文件 SHA256 必须相同：`gui_agent_loop.py`、`task_world.py`、`app.js`、`app.css`。报告必须列出两份 runner 源码提交，不能再声称五个文件在所有试验完全一致。
