## G08：五次均在编辑后的返回导航上停滞

本轮 G08 新增 5 次有效运行，成功 0 次、失败 5 次，每次均执行 60 个动作。
五轮的前三步几乎相同：打开目标客户 C-71、进入 Edit draft、点击 Chrome 的后退按钮。
全部 300 个动作由 282 次 click、15 次 key、3 次 scroll 组成，没有 type，也没有 done。
五轮没有通道重试、动作执行异常或动作 JSON 解析失败。

第 1、2、5 轮业务审计为空；第 3、4 轮各保存一次旧资料草稿（8 Keizersgracht / Amsterdam / 1011 AB / Phone），没有 publish。
五轮均未改变另一个客户、客户身份或活动记录。失败发生在目标资料没有更新和发布。
各轮最长连续相同截图段分别为 32、21、31、21、31 张；这表明大量动作未改变可见界面。

人工核查了原始第 3 轮 step03.png（编辑表单）和 step27.png（保存旧草稿后返回资料页）。
step27.png 中最新地址仍清晰可见，随后 agent 又点击 Edit draft，继续返回循环。
可通过本地 VIEWER.html 切换 G08 第 3 次查看对应动作。

源码核查：app.js 的客户视图切换直接替换页面内容，没有 pushState / popstate；编辑页只有 Save draft，没有 Cancel。
Chrome 后退并不等同于返回客户资料视图。刷新以及保存草稿可以重新到达其他视图，原始轨迹中也出现了这些恢复路径，但没有接着完成资料更新。

这与当前 agent 跨页面保留信息和摆脱无效操作循环的不足相符，但本轮没有改变历史截图、记忆或页面导航做配对实验，不能据此把根因单独归于模型。
现有框架仅保留最新截图和最近六个动作，是解释这些结果时必须声明的条件。

## G10：五次均在读取政策后重入窗口，没有提交审批

本轮 G10 新增 5 次有效运行，成功 0 次、失败 5 次，每次均执行 60 个动作。
合计 204 次 scroll、87 次 click、9 次 drag，没有 type 或 done。
五轮的 ack 次数分别为 4、5、4、4、5，approve 次数全部为 0；最终均已读政策，但没有审批交付。
五轮没有通道重试、动作执行异常或动作 JSON 解析失败。

第 1 轮有效失败，用完 60 步。43 次 scroll、15 次 click、2 次 drag；业务审计只有 4 次 ack，没有 approve。
33 个 scroll 动作带 x/y 字段；原版工具只在当前鼠标位置滚动，会忽略这些额外坐标。
模型在无效滚动后曾通过点击或拖动滚动条到达政策底部。

人工核查了第 1 轮 step17.png：Manager / EXP-7 例外条款清晰可见；随后第 17 步点击已读。
step30.png 显示已读状态及已展开的审批路线下拉框，包含 Manager 选项，但后续又回到政策窗口。
因此这轮不能简单描述成“一直未读到规则”，它曾到达规则、确认已读，仍未完成审批。

第 5 轮 step16.png 显示已经选中 Manager，Reason code 仍空。随后 agent 重开政策并再次 ack；step22.png 显示路线回到 Standard。
源码中的 ack() 调用 approval() 重新构造表单，会把路线和理由重置。这个界面行为与 agent 反复重读政策共同造成了已完成选择被丢弃；它不是 OS 差异。
工具说明明确 scroll 在当前鼠标处执行，而模型持续附加被忽略的 x/y，也是已观察到的接口使用问题。
这些证据支持“信息保持、操作恢复、表单状态重置及接口理解共同相关”的诊断，不能据此分离出模型单独的因果贡献。

## 结论范围

这是当前 agent、工具接口、历史策略及 60 步预算共同条件下的重复试验。
不能把两道题当成两条已证实独立机制；两者可能共享跨页面信息保持问题。
两题是受控的合成业务网页，在真实 GitHub Ubuntu 桌面中通过物理鼠标键盘操作。
本轮没有跨操作系统的成对复测，不证明任何 OS 特有失败，也不满足原 EnvShift 静默 OS 翻转题的门槛。
